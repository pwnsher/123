KALSHI PERP INTEGRATION — PRODUCTION RUNBOOK (Step 6)
=====================================================
The bot places NO orders. It posts callouts and records paper calls. The only production
effect the perp system can ever have is to SUPPRESS an already-valid legacy call.
It cannot create a call, flip a side, change size, stops, entry mode or timing.

Current state: no real Step 3 candidate -> no Step 4 policy -> no Step 5 candidate ->
no promotion -> live veto INACTIVE. The bot behaves exactly as it always has.

-----------------------------------------------------------------------------------------
LIFECYCLE (each step must succeed before the next; commands are Windows "py")
-----------------------------------------------------------------------------------------
 1. Run the bot normally to collect telemetry:        py kalshi_bot.py
 2. Label settled markets (repeat, e.g. hourly):      py label_binary_outcomes.py
 3. Step 3 statistical analysis:                      py analyze_perp_predictive.py
       -> analysis_output/perp_candidate_manifest.json  (often [] — that is a valid result)
 4. Step 4 build a frozen shadow policy (if any):     py build_perp_shadow_policy.py
 5. Collect NEW shadow data by running the bot for at least a week.
 6. Step 4 prospective validation:                    py analyze_perp_shadow.py
       -> needs SHADOW_VALIDATED_CANDIDATE to continue. KEEP A COPY of
          analysis_output/perp_shadow_report.json (Step 5 records its SHA-256).
 7. Step 5 freeze an experiment:                      py build_perp_integration_experiment.py
 8. Collect NEW data again (>= 14 days) by running the bot.
 9. Step 5 validation:                                py analyze_perp_integration.py
       -> needs PROBABILITY_OVERLAY_VALIDATED in analysis_output/perp_integration_candidate.json
10. Manual promotion (explicit, offline, creates an artifact only):
       py promote_perp_integration.py --experiment-id <id> --confirm LIVE_VETO_ONLY
       A promotion expires (default 14 days, max 30). There is no auto-renewal.
11. Check readiness without activating anything:      py check_perp_deployment.py
       Expect READY_BUT_DISABLED.
12. Explicitly enable for THIS shell only, then restart the bot:
       cmd:        set PERP_LIVE_VETO_ENABLED=1 && py kalshi_bot.py
       PowerShell: $env:PERP_LIVE_VETO_ENABLED = "1"; py kalshi_bot.py
       Do not add it to permanent system environment variables.
13. Confirm the startup banner says:
       PERP LIVE VETO: ACTIVE — VETO ONLY
    Anything else (OFF / PROMOTION PRESENT, ACTIVATION DISABLED / REFUSED) means the bot is
    running legacy behaviour, which is safe.

-----------------------------------------------------------------------------------------
EMERGENCY SHUTDOWN OF THE PERP VETO (does NOT stop the watcher)
-----------------------------------------------------------------------------------------
  Create the kill file in the bot's working directory:
      cmd:        type nul > DISABLE_PERP_LIVE_VETO
      PowerShell: New-Item DISABLE_PERP_LIVE_VETO
  At the next candidate signal the veto latches OFF for the rest of the process and every
  legacy call proceeds. Deleting the file does NOT re-enable it: remove the file and restart.

  To stop trading activity entirely, use the EXISTING watcher pause control in the dashboard.
  Pausing the watcher and disabling the perp veto are separate actions; do not confuse them.

-----------------------------------------------------------------------------------------
AUTOMATIC SAFETIES (no action needed)
-----------------------------------------------------------------------------------------
  * Missing/stale/unscorable perp data  -> FAIL OPEN (the legacy call proceeds), logged.
  * Invalid, expired, synthetic or tampered promotion -> the gate never activates.
  * Strategy drift (any change to strategy constants or functions vs the Step 5 baseline)
    -> activation refused.
  * 3 consecutive internal gate errors, >35% blocked or >50% fail-open in the last 50 scored
    signals -> the veto latches OFF for the process; legacy calls continue.
  * A changed promotion file is never hot-reloaded; a restart is required.

SUPPORTED PYTHON (Step 6.1)
  Intended: CPython 3.10 - 3.13. Validated in the release environment: CPython 3.12.3 only
  (full Stage 1-12 suite + clean extraction). Python 3.13 was NOT available there; its AST
  differences (ast.dump show_empty=False; FunctionDef.type_params) are covered by explicit
  cross-schema regression tests. The strategy fingerprint is format v2 (canonical_ast_v2_sha256):
  a different Python minor version is NOT itself a reason for rejection — only a real change to
  strategy constants or functions is. check_perp_deployment.py shows the runtime Python as a
  diagnostic.
