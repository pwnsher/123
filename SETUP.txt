PERP TELEMETRY (Step 1 — passive, read-only research recorder)
  What it is: every poll cycle, the watcher hands its binary results to a background
  thread that fetches Kalshi perpetual-futures market data and writes one row per coin
  to kalshi_perp_telemetry.csv (perp bid/ask/mid/last/mark, Kalshi reference/index price,
  premium, funding-rate estimate, 30/60/180s perp & spot returns, perp-minus-spot lead,
  plus the binary ticker, strike, p_up/conf/fav, edge, signal and reason so rows can be
  joined to market outcomes later).

  It is READ-ONLY and OBSERVATIONAL. It places no orders (perp or binary), touches no
  margin/leverage/transfers, and cannot affect signal, confidence, p_up, edge, stops,
  sizing, maker/taker, timing, calls, Discord posts, or the backtest. evaluate() never
  reads it. It runs off-thread, so even a hung perp endpoint cannot delay the watcher.

  Data source (docs.kalshi.com, Perps API): GET /trade-api/v2/margin/markets and
  GET /trade-api/v2/margin/funding_rates/estimate — both documented as public (no key).
  No environment variables are required. Perp tickers are auto-discovered; if discovery
  is ambiguous, set e.g.  $env:KALSHI_PERP_TICKER_BTC = "<exact ticker>".
  Optional: $env:KALSHI_PERP_API_BASE (e.g. the demo host).

  Units: perp prices and index_price are Kalshi PER-CONTRACT dollars; spot_price is
  Coinbase USD per coin, so don't compare their levels. premium_bps = perp_mid vs Kalshi's
  own reference price. Returns (bps) are ratios and ARE comparable. base_p_up is a percent.
  Blank CSV cells mean "not available" (never a fabricated 0). funding_rate is Kalshi's
  estimate for the in-progress period, logged as returned.

  If perp data is unavailable: the binary bot runs exactly as before; rows are still
  written with source_status = error / unavailable / stale and a source_error reason.
  Statuses: fresh | stale (older than PERP_STALE_SECONDS) | unavailable | error | disabled.
  Size: ~4 rows per poll cycle (roughly 20-40 MB/day at a 4 s poll).

  Disable: set PERP_TELEMETRY_ENABLED = False in kalshi_dashboard.py, or
           $env:KALSHI_PERP_TELEMETRY = "0"
  This is unproven research data — nothing here claims perps improve profitability.

PERP TELEMETRY — STEP 2 (causal alignment + data quality; still observation only)
  Timing: a background sampler polls Kalshi perps every PERP_SAMPLE_SECONDS into a
  bounded 30-minute history. Each binary row uses the newest perp snapshot that was
  fully received AT OR BEFORE that row's spot price arrived (feature_end_ts_epoch_ms),
  and only if it is no older than PERP_ALIGNMENT_MAX_LAG_SECONDS (8 s). A snapshot
  received even 1 ms after the spot observation is never used.
  "causal_*" means "computed only from data available at that time" — it does not
  claim that perps lead or cause spot moves. That is tested in Step 3.

  New columns (schema v2): versions/session/cycle ids, spot receive time + latency,
  perp snapshot time + lag, causal_pair_ok, analysis_ready, quality_flags (';'-separated
  codes), spread, basis measures, premium changes & z-scores, causal returns, momentum
  gaps (perp return - spot return), realized volatility and vol-shock ratios, funding
  availability/age, queue counters. All Step 1 columns are kept unchanged.
  An existing Step 1 CSV is renamed to *.schema-<time>.bak on first run (never mixed).

  analysis_ready = binary row OK + spot price & time present + a prior perp snapshot
  within the lag limit + that snapshot fresh + two-sided mid + Kalshi index present.
  Longer-window features (e.g. premium_z_15m) may still be blank while warming up.

  Data-quality report (reads the CSV only; no predictive analysis):
    py analyze_perp_quality.py
    py analyze_perp_quality.py --file kalshi_perp_telemetry.csv --json quality_report.json

  Tests:  py test_stage8.py     (or py run_all_tests.py for stages 1-8)

PERP TELEMETRY — STEP 2 v2 (schema 3 / feature_version step2_v2): VOLATILITY-REGIME RESEARCH
  Why: a +20 bp perp move means something different in a quiet market than in a violent one.
  These columns let Step 3 test that. They are TELEMETRY ONLY: nothing in the bot reads them,
  and they can only ever matter through Step 3 -> Step 4 -> Step 5 -> manual promotion ->
  LIVE_VETO_ONLY, exactly like every other perp feature. Volatility is treated as a
  reliability/regime variable, never as bullish or bearish.

  New columns (all computed only from data available at feature_end_ts_epoch_ms):
    perp_momentum_z_{30,60,180}s   causal_perp_ret_h / (perp_rv_300s_bps * sqrt(h/60))
    spot_momentum_z_{30,60,180}s   same for spot (a CONTROL in Step 3, never a candidate)
    momentum_gap_z_{30,60,180}s    momentum_gap_h / sqrt(sigma_perp_h^2 + sigma_spot_h^2)
                                   (a volatility-scaled disagreement measure, NOT a true z-score:
                                   perp and spot are positively correlated, so it is conservative)
    perp_spread_median_5m_bps      median two-sided spread of the snapshots in the 300 s BEFORE
                                   the selected one (>= 20 points spanning >= 240 s, same contract
                                   scale; one-sided/crossed books excluded)
    perp_spread_baseline_n         number of snapshots in that baseline
    perp_spread_ratio_5m           perp_spread_bps / perp_spread_median_5m_bps
    premium_stress_5m              |premium_z_5m|
    vol_regime                     LOW <0.5 | NORMAL | HIGH >=1.5 | EXTREME >=2.5 | UNKNOWN, from the
                                   max available RV shock ratio (perp 60v300 required; perp 60v900 and
                                   spot 60v300/60v900 when available). Observational only.
    perp_stability_state           STABLE | CAUTION | UNSTABLE | UNKNOWN, a transparent rule (no score):
                                   CAUTION at vol HIGH, |gap_z60| >= 1, premium stress >= 2.5,
                                   spread ratio >= 2; UNSTABLE at vol EXTREME, |gap_z60| >= 2,
                                   premium stress >= 4, spread ratio >= 4, or any two CAUTIONs.
                                   STABLE needs all four inputs. Never fed to any probability.
    perp_stability_reasons         which rule(s) fired, ';'-separated
  RV is in bps per sqrt-minute; the 300 s RV is the normaliser (60 s reacts to the move itself,
  900 s adapts too slowly). A 300 s RV below 0.01 bps/sqrt-min gives a blank, never a clipped value
  (flag VOL_NORM_DENOMINATOR_TOO_SMALL). analysis_ready does NOT depend on these features warming up.
  New quality flags: VOL_NORM_DENOMINATOR_TOO_SMALL, INSUFFICIENT_SPREAD_BASELINE.
  Not available from the documented perps endpoints, so NOT recorded or inferred: open interest,
  liquidations, trade aggressor side, order-book depth.

  Upgrading from schema 2: the existing kalshi_perp_telemetry.csv is renamed to
  *.schema-<time>.bak on first write (never mixed). Step 3 refuses schema-2 rows; frozen Step 4
  policies built on schema 2 are refused by the shadow loader, the Step 5 builder, the promotion
  command and the live gate (never migrated). Re-collect telemetry and re-run the research chain.

  Dashboard: each coin card has one extra line "perp vol · stability (telemetry, observe only)":
  direction + 60 s normalised momentum, vol regime + shock ratio, spot/perp agreement, spread and
  premium stress, stability state (hover for the numbers, reasons and data freshness).

  Quality report (analyze_perp_quality.py) adds coverage of every new feature (overall, by coin,
  analysis_ready rows), regime / stability distributions and % UNKNOWN, the reason each new feature
  is blank, and extreme/pathological values (reported, never clipped).

  Tests:  py test_stage14.py    (or py run_all_tests.py for stages 1-14)

STEP 3 — OUTCOME LABELS + OFFLINE PREDICTIVE ANALYSIS (research only; changes nothing in the bot)
  1) Label settled markets (reads the telemetry, never modifies it; GET only):
       py label_binary_outcomes.py
       py label_binary_outcomes.py --telemetry kalshi_perp_telemetry.csv --output kalshi_binary_outcomes.csv
     Source: GET /trade-api/v2/markets/{ticker} -> market.result (same call the watcher uses).
     yes -> outcome_up 1, no -> 0, anything else -> unresolved (never guessed).
     Only asked once now >= close + 90 s. Final labels are cached and never refetched;
     --verify-final re-checks them and flags CONFLICTING_SETTLEMENT_RESULT instead of overwriting.
     Safe to run repeatedly (e.g. hourly).

  2) Analyse (two local CSVs only; no network):
       py analyze_perp_predictive.py
       py analyze_perp_predictive.py --telemetry kalshi_perp_telemetry.csv \
          --labels kalshi_binary_outcomes.csv --outdir analysis_output
     Writes analysis_output/: perp_predictive_report.json, perp_feature_screen.csv,
     perp_leadlag_report.csv, perp_candidate_manifest.json, perp_oof_predictions.csv.
     Fails loudly (exit 3) on a mixed/unknown schema or any causal-invariant violation.

  What it tests: one observation per market at 8/6/4/2 minutes before close (latest
  analysis-ready row at or before the target, <= 10 s early, never after). Nested
  logistic models scored out-of-sample on identical rows:
       A = recalibrated existing probability   B = A + matched spot control
       C = B + one perp feature (reliability features also get feature x base_logit)
  A perp feature only counts if C beats B (not merely A). Chronological walk-forward on
  whole close-time groups; train-only winsorise/standardise (within coin for ALL);
  ticker-clustered bootstrap; BH-FDR over the 8 predeclared primary features (step3_v2 added
  perp_momentum_z_60s, judged against spot_momentum_z_60s; all other schema-3 features are
  secondary and can never become candidates).
  step3_v2 also screens a predeclared 3-member INTERACTION family (perp_momentum_z_60s x
  perp_vol_shock_60v300, momentum_gap_z_60s x perp_vol_shock_60v300, perp_momentum_z_60s x
  perp_spread_ratio_5m) beyond both main effects and spot-control x modifier; BH within the
  family. Research only: never a candidate (perp_interaction_screen.csv). The report also
  describes the existing model's accuracy per vol_regime / stability state (descriptive only).
  Candidate status needs >= 500 markets, >= 100 of each outcome, >= 3 folds, positive
  Brier AND log-loss gain vs B, CI > 0, q <= 0.05, >= 75% sign consistency.
  An empty perp_candidate_manifest.json is a normal, valid result — expect
  INSUFFICIENT_DATA for the first days. No thresholds or trading rules are produced.

  Tests:  py test_stage9.py     (or py run_all_tests.py for stages 1-9)

STEP 4 — CANDIDATE PERP FILTERS + SHADOW-ONLY VALIDATION (nothing is ever enabled)
  Expected today: Step 3 has no real candidate -> no policy -> the bot runs exactly as before.

  1) After a Step 3 run on REAL data, freeze policies (offline, fails closed on any mismatch):
       py build_perp_shadow_policy.py
     Uses ONLY analysis_output/perp_candidate_manifest.json, and only cohort=first_signal
     candidates (fixed-horizon ones are reported NOT_CALL_FILTER_ELIGIBLE). Verifies file hashes
     against the Step 3 report, recomputes Step 3's out-of-fold results, and refuses data without
     real-collection provenance. Each candidate gets its own policy:
       conflict_score = P_C(favoured side) - P_B(favoured side)   (Step 3 MODEL C vs MODEL B)
       threshold = most conservative of the 5/10/15/20/25th percentiles of OOF conflict scores that
       passes count, 5-25% block-rate, >=5pp loss-enrichment, bootstrap-CI and BH gates.
     Output perp_shadow_policies.json: immutable, hashed, mode SHADOW_ONLY. Rebuilding with new
     data creates a NEW policy id; old policies are never edited.

  2) Live: the watcher loads perp_shadow_policies.json (if present) and, on the telemetry worker
     AFTER the real call was made, records the policy's ALLOW / WOULD_BLOCK / UNAVAILABLE verdict
     for the FIRST signal of each ticker in kalshi_perp_shadow.csv. WOULD_BLOCK changes nothing.
     Disable with $env:KALSHI_PERP_SHADOW = "0". Corrupt/synthetic policy files are ignored.

  3) Evaluate prospectively (offline; never retunes the frozen threshold):
       py analyze_perp_shadow.py
     -> analysis_output/perp_shadow_report.json. Only calls after the discovery cutoff count.
     Joins settlement (kalshi_binary_outcomes.csv) and actual paper P&L (kalshi_calls.json) by
     exact ticker. Unfilled maker orders are not trades. Needs >= 7 days, >= 200 settled calls,
     >= 30 would-block, >= 150 would-allow, >= 90% coverage, >= 75% retention.
     Best possible status is SHADOW_VALIDATED_CANDIDATE = eligible for Step 5 review only.

  Call journal: new calls now carry ticker + signal_ts (kalshi_calls.json and kalshi_trades.csv).
  An older trades CSV header is renamed to kalshi_trades.legacy-<time>.csv (kept, never mixed).

  Tests:  py test_stage10.py    (or py run_all_tests.py for stages 1-10)

DASHBOARD REAL-TIME PASS (presentation only; strategy, telemetry and live veto unchanged)
  * The watcher still evaluates every POLL_SECONDS (4 s). The page now re-reads the server's local
    state every ~1 s (self-scheduling, never overlapping, 5 s request timeout, keeps values on a
    failure and retries ~1/s), so each new result appears sooner. Strategy frequency is unchanged.
  * Countdown: computed in the browser every 250 ms from the market's absolute close time (r.close);
    no request. A background tab shows the correct time as soon as it is visible again.
  * Chart: 60 one-minute bars from /candles at start-up, re-synced every 60 s (was every ~15 s);
    the newest bar (line point or candle H/L/C) moves with the spot the watcher already observed
    (r.spot / r.spot_observed_ts), so the browser adds no Coinbase requests.
  * "spot N s" beside each countdown = age of the last spot observation (amber >= 5 s, red > 10 s);
    "data live / retrying" in the top bar = the browser's link to the local server. Display only.
  * /data, /ping, /candles send Cache-Control: no-store; /data is serialised under the lock and
    written to the socket outside it.
